# Nutcracker Plugin — Design Spec

**Status:** Draft, pending review
**Date:** 2026-09-02

## Goal

A Claude Code plugin, modeled on `superpowers`' planning skills
(`writing-plans` → `executing-plans`), that persists hierarchical task
plans as **ClickUp task hierarchies** via the `cum` CLI instead of local
markdown files. A plan is a parent ClickUp task; each implementation task
is a subtask; each task's bite-sized steps are a ClickUp checklist;
task ordering is a real ClickUp dependency graph (`cum tad`), not prose.

## Non-Goals (explicitly out of scope for v1)

- **No subagent-orchestration tier.** Superpowers' `subagent-driven-development`
  skill (per-task subagent dispatch, a ledger file, scoped re-reviews, a
  5-round fix loop, model-tier selection) solves "conversation memory
  doesn't survive compaction" with a bespoke ledger file. Nutcracker
  doesn't need that ledger: ClickUp *is* the persistence layer, and
  `cum d`/`cum ls`/`cum assigned` against a real task hierarchy survives
  compaction for free. If per-task subagent dispatch is wanted later, it's
  a clean add-on skill once the core two skills exist — not part of v1.
- **No multi-runtime shims.** Superpowers ships `.codex-plugin/`,
  `.cursor-plugin/`, `.devin-plugin/`, `.hermes-plugin/`, `.kimi-plugin/`,
  `.opencode/`, `.pi/` — these are auto-generated by superpowers' own
  `scripts/sync-to-codex-plugin.sh` etc., not hand-authored. Nutcracker
  targets Claude Code only; none of these are built.
- **No code-review skills.** Superpowers has `requesting-code-review`/
  `receiving-code-review` as separate, general-purpose skills unrelated to
  the plan-hierarchy mechanism specifically. Out of scope — this plugin is
  about the plan/task persistence layer, not code review.
- **No custom field / task-type modeling.** `cum tc --task-type` exists
  and could tag plan tasks with a custom "Plan"/"Implementation Task"
  type, but that requires the target workspace to have those types
  configured, which isn't guaranteed. v1 uses plain tasks + checklists +
  dependencies only — the ClickUp primitives every workspace has.

## Architecture

Three skills plus a force-load hook, directly mirroring superpowers'
shape:

| Superpowers | Nutcracker | Backing store |
|---|---|---|
| `using-superpowers` (SessionStart-forced) | `using-cum-planning` (SessionStart-forced) | n/a — routing skill |
| `writing-plans` | `writing-cum-plans` | ClickUp task hierarchy (via `cum`) |
| `executing-plans` | `executing-cum-plans` | Same hierarchy, read back via `cum` |

## Plan → ClickUp mapping

| Superpowers plan concept | Nutcracker / ClickUp equivalent |
|---|---|
| Plan file `docs/superpowers/plans/YYYY-MM-DD-feature.md` | Parent task (`cum tc "<Feature>" --list <list>`) |
| Plan header (Goal/Architecture/Tech Stack/Spec link/Global Constraints) | Parent task description (`--description`), written as markdown — `cum` renders markdown in descriptions |
| `### Task N: [Component Name]` | Subtask (`cum tc "Task N: <Component Name>" --parent <parent_id>`) |
| Task's Files/Interfaces block | Subtask description |
| `- [ ] Step 1: ...` / `- [ ] Step 2: ...` bite-sized steps | Checklist on the subtask (`cum chk create <subtask_id> "Steps"`, then `cum chk item-add <checklist_id> "Step 1: ..."` per step) |
| "Task 3 depends on Task 2" prose | Real dependency: `cum tad <task_3_id> --waiting-on <task_2_id>` |
| Marking a step done | `cum chk item-update <checklist_id> <item_id> --resolved true` |
| Marking a task done | `cum tss <subtask_id> "complete"` — checklist validation is **on by default** (blocks completion until checklist items are resolved unless `--force` is passed); do not pass `--force` as a matter of course, since that's the safety net this design relies on |
| Progress notes / ledger entries | `cum ca <task_id> "<note>"` (ClickUp comment) — no separate ledger file; the comment thread *is* the ledger, and it survives compaction because it's not in local session state |
| "Which tasks are unblocked / ready to work?" | `cum assigned` already computes and reports this (`Ready to start: N`, `Blocked: N` in its summary) — no bespoke readiness tracking needed |

## Component: plugin manifest & directory layout

```
clickup_framework/plugin/
  .claude-plugin/
    plugin.json
  hooks/
    hooks.json
    session-start.sh
  skills/
    using-cum-planning/
      SKILL.md
    writing-cum-plans/
      SKILL.md
    executing-cum-plans/
      SKILL.md
```

`plugin.json`: `name: "nutcracker"`, a one-line description ("Hierarchical
task planning and execution backed by ClickUp via the cum CLI"),
`version: "0.1.0"`, `author` matching `pyproject.toml`'s
("ClickUp Skills Development Team"), `keywords: ["clickup", "cum",
"planning", "task-hierarchy"]`.

This lives inside the `clickup_framework` repo (per your direction) but
is **not** installed by `cum install-skill` — that command installs
standalone skills into `~/.claude/skills/`, not plugins (which need a
`.claude-plugin/plugin.json`, live under `~/.claude/plugins/`, and are
enabled via `enabledPlugins` in settings, not a skill-copy). Installing
this plugin is a manual/documented step (`README.md` addition covering
"add `clickup_framework/plugin` as a local plugin directory" — the
`command`-source plugin type documented in the settings schema, or just
`cp -r clickup_framework/plugin ~/.claude/plugins/nutcracker` for now).
Wiring an automated installer is a fair follow-up but out of scope here
— it's a second, separate mechanism from everything `install-skill`
already does, and conflating them risks breaking the existing installer.

## Component: SessionStart hook

`hooks/hooks.json`:
```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|clear|compact",
        "hooks": [
          {
            "type": "command",
            "command": "\"${CLAUDE_PLUGIN_ROOT}/hooks/session-start.sh\"",
            "shell": "bash",
            "timeout": 15
          }
        ]
      }
    ]
  }
}
```

`hooks/session-start.sh`: adapted from superpowers' `hooks/session-start`
(verified byte-for-byte against the live file), trimmed to Claude-Code-only
(superpowers' script branches on `CURSOR_PLUGIN_ROOT`/`COPILOT_CLI` env
vars for cross-runtime output shape; nutcracker only needs the
`hookSpecificOutput.additionalContext` branch). Reads
`skills/using-cum-planning/SKILL.md` relative to `$CLAUDE_PLUGIN_ROOT`,
JSON-escapes it (backslash, quote, newline, CR, tab — same four-substitution
approach as the reference script), wraps it in a short banner, and prints
`{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": "..."}}`.
Must degrade gracefully (missing file, `$CLAUDE_PLUGIN_ROOT` unset) the same
way `cum-todo-sync`'s hook does — print a minimal valid JSON object rather
than a non-JSON error, so a broken hook can't corrupt session start for
every other hook running in the same batch.

## Component: `using-cum-planning` skill

**Frontmatter:** `name: using-cum-planning`, `description: Use when starting any conversation involving multi-step task planning or execution that should be tracked in ClickUp rather than local files — establishes routing to writing-cum-plans and executing-cum-plans.`

Short (this is force-loaded every session — token cost matters). Content:
- One-paragraph explanation: plans live in ClickUp, not local files; two
  skills, `writing-cum-plans` (spec → ClickUp hierarchy) and
  `executing-cum-plans` (ClickUp hierarchy → working code).
- **Explicitly does not duplicate `cum-cli` or `superpowers:using-superpowers`.**
  If `cum-cli` isn't already loaded (it's a separate personal skill, not
  bundled here), point to it via the `Skill` tool for baseline `cum`
  usage, rather than re-teaching it inline in a force-loaded hook.
- One-line pointer to `superpowers:using-git-worktrees` for isolation, if
  that plugin is present — nutcracker doesn't reinvent worktree isolation.
- A **verified command reference table** (below) inlined directly, since
  this is the one place guaranteed to load into every session and
  "ensuring correct usage" was the explicit requirement for this plugin.

## Component: `writing-cum-plans` skill

**Frontmatter:** `name: writing-cum-plans`, `description: Use when you have a spec or requirements for a multi-step task and want the plan tracked as a ClickUp task hierarchy instead of local files, before touching code.`

Procedure (mirrors superpowers' `writing-plans` structure, ClickUp-backed):

1. **Resolve the target list.** Run `cum show` to check for a configured
   current list. If none, ask the user which list (`cum ls-mgmt`/`cum
   flat <list_id>` to browse if they're unsure) — never guess a list ID.
2. **File Structure pass** (unchanged from superpowers — decide file
   boundaries before decomposing tasks) stays pure planning, no `cum`
   calls yet.
3. **Create the parent task:**
   `cum tc "<Feature Name>" --list <list_id> --description "<Goal/Architecture/Tech Stack paragraphs>"`
   — capture the returned task ID from the command's own output (`cum tc`
   prints the created task's ID; parse it from console output or use
   `-O json` for a machine-readable ID if scripting the creation).
4. **Per implementation task:**
   `cum tc "Task N: <Component>" --parent <parent_id> --description "<Files/Interfaces block>"`
5. **Steps as a checklist:** `cum chk create <task_id> "Steps"`, then one
   `cum chk item-add <checklist_id> "Step k: <description>"` per bite-sized
   step (test-first steps included — "Write failing test", "Verify it
   fails", "Implement", "Verify it passes", "Commit" as separate items,
   matching superpowers' granularity).
6. **Dependencies:** for each task that must wait on another,
   `cum tad <task_id> --waiting-on <other_task_id>` — **not**
   `--depends-on` (doesn't exist, confirmed gotcha from the `cum-cli`
   skill and this session's own history).
7. **Self-review** (unchanged from superpowers: spec coverage, placeholder
   scan, type/interface consistency across tasks) — done by reading back
   the created hierarchy with `cum d <parent_id>` before handing off, not
   just trusting what was just written.
8. **Execution handoff:** report the parent task ID and tell the user
   "plan created as ClickUp task `<parent_id>`; use `nutcracker:executing-cum-plans`
   to work through it."

No local plan file is written. No ledger. The comment thread + task
status + checklist state on the parent task IS the plan's live state.

## Component: `executing-cum-plans` skill

**Frontmatter:** `name: executing-cum-plans`, `description: Use when you have a ClickUp task hierarchy created by writing-cum-plans and need to implement it task-by-task, tracking progress in ClickUp.`

Procedure (mirrors superpowers' `executing-plans`):

1. **Load and review:** `cum d <parent_id>` to read the full plan
   (description + subtasks). Review critically — same "raise concerns
   before starting" gate as superpowers.
2. **Find ready work:** `cum d <parent_id>` (or `cum assigned` if the
   tasks are assigned to the current user) reports blocked vs. ready
   subtasks directly — dependency resolution is `cum`'s job, not this
   skill's. Work tasks in the order `cum` reports as unblocked, not
   positional order in the hierarchy.
3. **Per task:**
   - `cum tss <task_id> "in progress"` if that status exists on this
     list (**check first with `cum d`** — per the `cum-cli` skill's own
     documented gotcha, many lists only have "to do"/"complete"; don't
     assume "in progress" exists, fall back to a progress comment via
     `cum ca` if it doesn't)
   - Follow each checklist step exactly; after finishing a step,
     `cum chk item-update <checklist_id> <item_id> --resolved true`
     immediately (don't batch these at the end — the checklist state IS
     the progress record, same reasoning as "commit frequently")
   - Run verifications as the step specifies
   - `cum tss <task_id> "complete"` once all steps are done — this fails
     closed if any checklist item is still unresolved (`cum tss`'s
     checklist validation, on by default); treat that failure as a
     correctness signal, not an obstacle to route around with `--force`
4. **Progress notes:** `cum ca <task_id> "<note>"` for anything worth a
   human seeing later that doesn't fit a checklist item (a deviation from
   the plan, a decision made, a blocker hit) — this is nutcracker's
   equivalent of the ledger, and it's visible to humans in ClickUp without
   them needing repo/session access.
5. **When to stop and ask** (unchanged from superpowers): blocker,
   critical plan gaps, unclear instruction, repeated verification failure.
   Never silently route around a blocked dependency by working an
   out-of-order task — if `cum` reports everything blocked, that's a plan
   defect, stop and ask.
6. **Completion:** once the parent task's own status can move to
   "complete" (all subtasks done), do so and report the parent task ID
   back to the user as the record of what was built.

## Correct-usage reference (embedded in `using-cum-planning`)

Verified live against the installed `cum` CLI in this session (not from
memory) — this table is the actual deliverable behind "ensuring correct
usage":

| Task | Correct command | Note |
|---|---|---|
| Create parent task | `cum tc "<name>" --list <list_id> --description "<text>"` | `--list` not required if `--parent` given |
| Create subtask | `cum tc "<name>" --parent <parent_id> --description "<text>"` | |
| Create checklist | `cum chk create <task_id> "<name>"` | |
| Add checklist item | `cum chk item-add <checklist_id> "<name>"` | needs `--task <id>` only if `checklist_id` is a positional index rather than the real ID |
| Resolve checklist item | `cum chk item-update <checklist_id> <item_id> --resolved true` | boolean flag — `true`/`false`/`1`/`0`/`yes`/`no` all parse correctly (fixed in commit `e1d1531`); anything else is rejected, not silently coerced |
| Add dependency | `cum tad <task_id> --waiting-on <other_id>` | **not** `--depends-on` — doesn't exist |
| Add dependency (inverse) | `cum tad <task_id> --blocking <other_id>` | **not** `--blocks` — doesn't exist |
| Set status | `cum tss <task_id> "<status>"` | status names are **list-specific** — check with `cum d <task_id>` first, never assume "in progress" exists |
| Comment | `cum ca <task_id> "<text>"` | |
| Read hierarchy | `cum d <parent_id>` | shows subtasks and (for the assignee) blocked/ready state |

## Error handling

- **`cum` not on PATH / no credentials:** both skills should fail the
  same way any other `cum`-dependent workflow does — surface the error
  from the command, don't swallow it. No special handling needed; this
  isn't a background hook where silent degradation is required (see
  `cum-todo-sync`'s hook for where that pattern belongs — it doesn't
  apply here since these are interactive, foreground skills).
- **Partial hierarchy creation failure** (e.g. parent task created,
  then a subtask creation fails partway through `writing-cum-plans`):
  report the parent task ID and which subtasks succeeded so the user can
  decide whether to retry the remaining ones or clean up — do not
  auto-delete the parent task. Task deletion is destructive and this
  plugin should never do it without being asked.
- **Dependency cycle:** if `cum tad` rejects a dependency (API-level
  cycle detection, if `cum`/ClickUp enforce it) or if `cum d` reports
  every subtask blocked with no ready task, `executing-cum-plans` treats
  this as a plan defect per its "when to stop" rule — not something to
  silently work around.

## Testing plan

- **Skill content correctness:** every `cum` command example in both
  skills must be re-verified against `cum <command> --help` at
  implementation time (not just copied from this spec) in case the CLI
  has changed since this spec was written — this spec is dated, the CLI
  isn't guaranteed to match.
- **Hook:** pipe-test `hooks/session-start.sh` directly (`echo '{}' |
  bash hooks/session-start.sh`) and confirm valid JSON output, same
  verification method already used for `cum-todo-sync`'s hook.
- **End-to-end:** use the `skill-cli-tester` skill (already available in
  this environment — "Test Claude skills end-to-end using the Claude CLI
  in print mode") to drive a real `writing-cum-plans` → `executing-cum-plans`
  cycle against a real (test/throwaway) ClickUp list, verifying the
  created hierarchy matches the mapping table above and that checklist/
  status/dependency state ends up correct — not just that commands ran
  without error.
- **Plugin loads cleanly:** confirm `plugin.json` validates and the
  SessionStart hook fires without breaking other hooks in the same
  session (test alongside `cum-todo-sync`'s hook, since both may be
  installed at once).
